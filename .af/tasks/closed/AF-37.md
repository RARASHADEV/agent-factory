# Engineer subprocess exits non-zero after successfully completing work

## Summary

In the sdlc pipeline's implement phase, the engineer agent completes its full
workflow — creates a feature branch, commits code changes, pushes to origin, opens
a PR, moves the task file from `in-progress/` to `ready-for-qa/` — and then the
subprocess **exits non-zero**. The pipeline runner treats this as a failure,
records `failureReason: spawn_error`, and aborts the pipeline before the verify
phase runs.

## Reproduction

1. Run `af pipeline run sdlc --task AF-33` with the AF-35 workaround applied
2. Observe the engineer phase:
   - Commit created and pushed (confirmed via `git log`)
   - Branch `engineer/AF-33` created on origin
   - PR opened (confirmed via `gh pr list`)
   - Task file moved to `.af/tasks/ready-for-qa/`
3. Observe the pipeline output: `✗ spawn exited non-zero`
4. Observe `pipeline-state.json`: `"implement": { "status": "failed",
   "failureReason": "spawn_error" }`

Captured 2026-04-15 on AF-33: PR #8 opened cleanly by engineer, but pipeline
marked implement phase failed. Verify phase never ran.

## Blocked by

**AF-36** — the engineer's `agent.log` was stashed by `git stash -u`, so we
currently have zero visibility into what exit code was returned or why. Fix AF-36
first to unblock diagnosis.

## Hypotheses (pre-log-access)

1. A late step in the engineer's flow (e.g. `af sync --mode push`, a docs edit, a
   test-runner invocation) failed and the agent didn't swallow its exit code.
2. The SDK session returned a non-zero signal for reasons unrelated to task
   success (rate limit, timeout, tool-use exception).
3. A post-action hook (`src/lib/post-action-sync.ts`) threw after the agent had
   already produced its deliverables.
4. The agent's final `result.json` write failed (permissions, missing dir, race)
   and the runner treats that as fatal.

None of these can be confirmed without the engineer's agent.log.

## Suggested approach (Architect)

1. Land AF-36 first (gets logs back)
2. Re-run the pipeline on AF-33 (fresh) and inspect:
   - exit code of the engineer subprocess
   - last ~100 lines of `.af/output/AF-33/engineer/agent.log`
   - whether `.af/output/AF-33/engineer/result.json` was written
3. Based on evidence, fix either the runner (swallow benign non-zero exits,
   validate based on result.json existence + content) or the engineer agent
   (proper exit code handling).

## Acceptance

- [ ] Engineer phase spawn returns 0 when the agent has successfully produced
      its deliverables (commit + PR + task move + result.json with gate signal)
- [ ] When the engineer genuinely fails, spawn still returns non-zero (we don't
      want to paper over real failures)
- [ ] Verify phase runs after a successful implement phase (end-to-end pipeline
      run succeeds on AF-33 or an equivalent trivial task)
- [ ] Root cause of the non-zero exit is documented in this ticket's Log before
      closure
- [ ] Regression test covers the successful-implement → verify transition
