# Core-function refactor (presentation-free ops)

> **Epic:** AF-53 — AF Service over HTTP (`af serve`) · **Stage B prerequisite** · **Seq 5 (gate for Stage B breadth)**
> **Design:** `docs/designs/AF-53-service.md` §3.1 (one engine, thin adapters) + Invariant · **Flag:** n/a (refactor, no behaviour change)
> **Depends on:** — (independent; can start in parallel with Stage A) · **Blocks:** AF-59, AF-60

## User Story
As an **AF engineer**, I want each command's logic in a presentation-free core function that returns structured data, **so that** the CLI and the HTTP service share one engine and can never drift in behaviour.

## Context
The enabling refactor for exposing "all commands" without duplicating logic. Some already exists (AF-26 separated pipeline logic; `orchestrateCommand` is glue over an engine); the rest — `projects`, `status`, `task` — needs lifting so the CLI adds console formatting and the service adds JSON over the **same** op. **Invariant:** no business logic in HTTP handlers — a handler validates input, calls a core op, returns/enqueues its result.

## Acceptance
- [ ] `projects`, `status`, and `task` logic lifted into core ops that return data (no `console.*` inside the op).
- [ ] CLI commands re-expressed as thin formatters over those ops; existing CLI output/behaviour unchanged (regression-safe).
- [ ] Ops are importable by the service layer (enables AF-59/AF-60) and prove the parity acceptance (design test 7).
- [ ] No feature-flagged behaviour change — pure refactor.

## Sequencing
- **Depends on:** nothing — **can run in parallel with Stage A (AF-54–57).**
- **Blocks:** AF-59 (query routes) and AF-60 (mutation routes) — both mount on these ops.
- **Note:** landing this early de-risks Stage B; Stage B is "mostly mechanical once the refactor exists."
