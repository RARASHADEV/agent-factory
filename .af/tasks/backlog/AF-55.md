# File-backed durable job registry + reconcile-on-boot

> **Epic:** AF-53 — AF Service over HTTP (`af serve`) · **Stage A (execution plane)** · **Seq 2 of 4**
> **Design:** `docs/designs/AF-53-service.md` §7, Decision 7 (storage), Decision 10 (retention), §14 R1 · **Flag:** `ENABLE_AF_53`
> **Depends on:** AF-54 (server skeleton) · **Blocks:** AF-56 (queue persists jobs here)

## User Story
As an **AF platform operator**, I want every dispatched job persisted in a durable registry that reconciles itself on boot, **so that** no job is silently lost when `af serve` restarts and orphaned work becomes re-dispatchable.

## Context
**Not SQLite** — `better-sqlite3` is not an AF dependency and project.md forbids databases (§14 R1). Use a **single-process file-backed registry** at `AF_SERVICE_DB` (default `~/.af/service.json`): an in-memory map hydrated on boot, persisted via atomic temp-file + `rename` (the atomicity AF already uses for task/pipeline state). The service owns the only writer, so there is no multi-writer contention. The §7 columns are the JSON record fields verbatim.

## Acceptance
- [ ] Record shape matches §7 (`id, kind, project, role, objective, status, output_dir, callback_url, caller, queued_at, started_at, completed_at, result`).
- [ ] Writes are atomic (temp + `rename`); a crash mid-write never corrupts the file.
- [ ] **Reconcile on boot:** rows still `queued` are re-queued; rows still `running` (orphaned by restart) → `failed` and re-dispatchable (design test 5).
- [ ] Terminal rows older than `AF_SERVICE_RETENTION_DAYS` (default 30) are pruned on a boot + daily sweep; younger and non-terminal rows survive (design test 11, Decision 10).
- [ ] No new runtime dependency added (Decision 7).
