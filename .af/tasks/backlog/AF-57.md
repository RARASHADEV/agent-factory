# Completion callbacks on every terminal state

> **Epic:** AF-53 — AF Service over HTTP (`af serve`) · **Stage A (execution plane)** · **Seq 4 of 4**
> **Design:** `docs/designs/AF-53-service.md` §5.2 · **Flag:** `ENABLE_AF_53`
> **Depends on:** AF-56 (queue emits terminal events) · **Blocks:** AF-61 (deploy)

## User Story
As **any client that submitted a job with a `callback_url`**, I want `af serve` to POST me the result exactly once on any terminal state, **so that** I never have to poll and never hang waiting on a worker that crashed or timed out.

## Context
Generic async result delivery — **no external/ORA dependency**. When a `POST /jobs` request includes a `callback_url`, the service POSTs the terminal result to it on **every** terminal state — `completed | failed | crashed | timeout` — with payload `{ jobId, status, result }` (the `callback_url` is recorded on the job row, AF-55). `callback_url` is **optional**: clients that omit it simply poll `GET /jobs/:id` (AF-56) instead, so this ticket is *not* a blocker for a poll-only MVP. The terminal transition is persisted to `job_events` (AF-69) **before** the callback fires (§5.4 ③).

## Acceptance
- [ ] Callback fires on all four terminal states: `completed | failed | crashed | timeout` (design test 4).
- [ ] Exactly once per job; killed/timed-out/crashed worker still produces one `failed` callback with **no hang** (design test 4).
- [ ] Payload is `{ jobId, status, result }`; success path delivers `completed` with the result body.
- [ ] Jobs submitted **without** a `callback_url` are unaffected — result is retrievable via `GET /jobs/:id`.
- [ ] Callback delivery failures are retried/logged (recorded as `callback_failed` in `job_events`, AF-69), never silently dropped.
