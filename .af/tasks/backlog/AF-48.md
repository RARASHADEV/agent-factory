# Wire orchestrator to a production entry point

## Objective
Connect the orchestration engine (AF-46) to real execution and expose it to users. Today the engine ships as a library with an **unwired seam**: `AfCliExecutor` is never constructed outside tests, nothing binds its `AfCliDispatch` to `dispatchAgent` (AF-42), and there is no `af orchestrate` CLI command. As a result the per-step `backend` attribution plumbed by AF-FIX-A6 is never exercised in production, and the engine cannot be invoked end-to-end by a user.

## Context
Epic AF-41. Surfaced during review of PR #18 (integration/af-orchestration) as caveat to review finding A6. Spec: `docs/tech-design-orchestration.md` §2.1 (routing), §5.1 (Executor seam), §5.2 (orchestrator interface), §7 (AF CLI programmatic dispatch surface).

The pieces all exist and are unit-tested in isolation:
- `src/lib/execution.ts` — `dispatchAgent(config, opts)` returns `{ backend, output, usage, success }`.
- `src/lib/executor.ts` — `AfCliExecutor` takes an injected `AfCliDispatch` and threads `backend` into `AgentResult`.
- `src/lib/orchestrator.ts` — `createOrchestrator(executor)` / `Orchestrator.run(domain, objective, opts)`.

What's missing is the glue and the user-facing command.

## Acceptance
- [ ] A concrete `AfCliDispatch` implementation resolves an agent slug → execution frontmatter → `dispatchAgent`, returning `{ output, usage, backend }`
- [ ] `AfCliExecutor` is constructed with that dispatch in a production code path (not just tests)
- [ ] New `af orchestrate <domain> <objective>` CLI command runs the orchestrator end-to-end and prints `stopReason`, `totalUsage`, per-step `backend`, and finalizer verdict
- [ ] `--dry-run` flag surfaces the plan without dispatching (delegates to `OrchestrateOptions.dryRun`)
- [ ] Per-step `backend` is populated (never `'unknown'`) on a real run — verifying the AF-FIX-A6 path end-to-end
- [ ] Guarded by a feature flag in `src/lib/constants.ts` (e.g. `ENABLE_AF_48`), default off until verified
- [ ] Integration test exercises the wired executor against a stub dispatch (no live models); manual verification against a local Ollama/vLLM domain documented in the ticket log

## Notes
- This is the ENGINEER (backend/CLI) scope only. The agent-editor UI (AF-47) and `web/` changes are tracked separately and are a nested git repo not carried by the superproject PR.
- Keep model/backend routing in AF CLI (`dispatchAgent`) — the executor and orchestrator must stay model-agnostic (§2.1).
