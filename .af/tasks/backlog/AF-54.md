# AF adopts Loka-assigned ticket numbers (stop minting local numbers)

> Renumbered from AF-52 → AF-54 during the 2026-06-03 bookkeeping pass: AF-52 had
> collided with the local UX-design task (also numbered 52). Loka source-of-truth
> ticket retained content + priority; the UX task keeps AF-52.

**Companion to LOK-30** (Loka-side fix). This is the AF half.

**Context:** AF and Loka run independent ticket-number counters, causing duplicate numbers across systems (e.g. AF minted ORA-160 while Loka already had ORA-160). Decision: **Loka is the source of truth for task identity.** LOK-30 makes Loka the sole authoritative allocator that returns the allocated `ticket`/`ticketNumber`/`id` on create.

**This ticket — AF must stop minting its own numbers and adopt Loka's:**
1. On `af task create`, take the `ticket` / `ticketNumber` Loka returns from `POST /api/v1/tasks` and persist it as the task's `loka-ref` / frontmatter identity. Do not generate a local number.
2. Remove / retire AF's local counter logic (the abandoned `AF-13-counter-fix.md` `syncCounters()` + "pass ticket on push create" approach is dead — Loka ignores supplied numbers by design).
3. Ensure create is Loka-first: if Loka is unreachable, fail or defer rather than assigning a provisional local number that can later collide.

**Dependency:** Blocked by LOK-30 (Loka must return the authoritative identity first).

**Out of scope:** Cleanup of existing diverged duplicates (e.g. ORA-160) — separate data-fix task.

Related: AF-13 (counter-fix never shipped), AF-12/LOK-27 (bidirectional sync), AF-18/LOK-29 (webhooks), AF-30 (open push bug — same surface, different field).
