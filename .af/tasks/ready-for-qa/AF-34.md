# Pipeline Flow 7: Pause and resume running pipelines

## User Story

As a user running a long autonomous pipeline (30+ min, multiple agent spawns), I want to pause it between phases and resume it later — so I can inspect intermediate artifacts, review a phase's output before the next one burns tokens, or stop burning compute when I notice something is off without losing all progress.

## Objective

Add `af pipeline pause <ticket>` and `af pipeline resume <ticket>` commands, plus the runner changes and schema changes required to support them cleanly.

## Context

**Split out from AF-28.** When AF-28 (pipeline status command) was scoped, its Solution section mentioned four overall statuses — *running, completed, failed, paused* — but the underlying `PipelineStatus` type only has three (`'running' | 'completed' | 'failed'`) and there is no pause mechanism anywhere in the runner. AF-28 was descoped to stay read-only; pause is its own feature and lives here.

Adding pause interacts with several modules (runner, state schema, status renderer, audit events) and benefits from its own design pass.

**Related:**
- AF-26 — pipeline runner (where pause has to land)
- AF-27 — gate evaluation + retry (nothing to do here, but the retry loop is the other thing that can "pause" a phase conceptually — design must not collide)
- AF-28 — pipeline status command (will gain a new status to render once this lands)

## Solution (high-level sketch — Architect to detail in design phase)

1. **New commands**
   - `af pipeline pause <ticket>` — request a pause. Writes a sentinel (e.g. `.af/output/<ticket>/pause.request`) and/or sends a signal to the runner process.
   - `af pipeline resume <ticket>` — clears the sentinel. If the original runner process is gone, spawns a new run via the equivalent of `--from <next-phase>` logic.

2. **Runner changes**
   - Between phases, the runner checks for a pause request. If present: mark state `paused`, persist, exit cleanly (or wait if the process is still alive — decision for the designer).
   - **Mid-phase pause is explicitly out of scope for v1.** A phase always runs to completion before pause takes effect. Document this.

3. **Schema changes**
   - Extend `PipelineStatus` with `'paused'`.
   - Add `pausedAt?: string` and `resumedAt?: string` to `PipelineState` for audit visibility.

4. **Renderer**
   - AF-28's status command gets a new icon + rendering branch for `paused`. Trivial — only needs the schema extension.

5. **Durability**
   - Decide: does pause require the `run` process to still be alive, or is it durable across process exits? Recommend: **durable** — pause = "stop at the next phase boundary AND don't resume until the user asks." This matches user intent and avoids coupling to process lifecycle.

6. **Audit events**
   - `pipeline.pause`, `pipeline.resume` added to the `AuditEvent` union.

## Acceptance

- [x] `af pipeline pause <ticket>` marks a running pipeline as `paused` at the next phase boundary (does not interrupt the currently-running agent subprocess)
- [x] `af pipeline resume <ticket>` continues a paused pipeline from the next unfinished phase, re-using prior phases' artifacts
- [x] Pause is durable: if the runner process exits while paused, `resume` can still continue the run in a fresh process
- [x] `af pipeline status <ticket>` (AF-28) renders the `paused` state clearly
- [x] Attempting to `pause` a completed or failed pipeline is a no-op with a clear message
- [x] Attempting to `resume` a non-paused pipeline is a no-op with a clear message
- [x] Audit log records `pipeline.pause` and `pipeline.resume` events with timestamps
- [ ] Documentation: `docs/project-summary.md` or a pipeline guide describes the pause semantics (especially mid-phase behavior) — **deferred**: engineer role may not modify `docs/`. Hand-off to documentalist (see PR notes).

## Open Questions (for Product Analyst / Architect to resolve in design)

1. **Signal vs sentinel:** send SIGUSR1 to the runner, or poll a sentinel file between phases? Sentinel is more durable and simpler — recommend sentinel, but confirm.
2. **Mid-phase pause:** should a long-running agent spawn be interruptible? v1 says no. Is that acceptable, or is there a use case that demands it?
3. **Resume semantics:** does `resume` re-run the last-completed phase (safe re-entry) or start from the next pending phase? Recommend: next pending phase (artifacts already exist; re-running wastes tokens).
4. **Interaction with `--from`:** `af pipeline run <name> --task <T> --from <phase>` already exists (AF-26). Is `resume` just sugar over that, or a distinct code path? Recommend: shared implementation, different UX.
