# SQLite durable job registry + audit journal + reconcile-on-boot

> **Epic:** AF-53 — AF Service over HTTP (`af serve`) · **Stage A (execution plane)** · **Seq 2 of 4**
> **Design:** `docs/designs/AF-53-service.md` §7, Decision 7 (storage), Decision 10 (retention), §14 R1 · **Flag:** `ENABLE_AF_53`
> **Depends on:** AF-54 (server skeleton) · **Blocks:** AF-56 (queue persists jobs here), AF-69 (audit middleware writes the journal tables)

## User Story
As an **AF platform operator**, I want a durable SQLite database that defines the job + audit schema and reconciles itself on boot, **so that** no job is silently lost when `af serve` restarts and orphaned work becomes re-dispatchable — giving the queue (AF-56), callbacks (AF-57), and audit middleware (AF-69) a single durable store to build on.

## Context
**SQLite** (project-owner directive 2026-06-04; supersedes the earlier file-backed-JSON resolution — §14 R1, Decision 7). Use Node's **built-in `node:sqlite` (Node ≥ 22)** — a real SQLite engine with **no external/native dependency**, so nothing is added to `package.json` and the systemd deploy stays simple. **Do not add `better-sqlite3`.** DB path `AF_SERVICE_DB` (default `~/.af/service.db`); single writer, WAL mode for concurrent reads.

**Scope = the storage/data-access layer only.** This ticket creates the three §7 tables and the reconcile/retention logic and exposes a small data-access API. The *writing* of audit rows on every request and the `GET /audit` route belong to **AF-69**; the job registry rows are written by the queue (**AF-56**). Tables: `dispatch_jobs` (registry), `request_log` (cross-plane audit journal), `job_events` (lifecycle transitions).

## Acceptance
- [ ] DB opens via `node:sqlite`; **no** entry added to `package.json` dependencies; `better-sqlite3` absent (design test 15).
- [ ] Schema matches §7: `dispatch_jobs`, `request_log`, `job_events` with the listed columns + indexes; WAL enabled.
- [ ] **Reconcile on boot:** rows still `queued` are re-queued; rows still `running` (orphaned by restart) → `failed` and re-dispatchable (design test 5).
- [ ] **Retention default = keep everything** (`AF_SERVICE_RETENTION_DAYS=0`): nothing is pruned; `request_log` is never auto-pruned. A positive value prunes only terminal `dispatch_jobs`/`job_events` older than N days on a boot + daily sweep (design test 11, Decision 10).
- [ ] No new runtime dependency added (Decision 7).
