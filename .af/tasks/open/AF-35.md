# Pipeline runner reads stale task.filePath after status move → ENOENT in first phase

## Summary

`af pipeline run <name> --task <TICKET>` fails immediately at the first phase with
`ENOENT: no such file or directory` on the task markdown file whenever the task is not
already in `in-progress`. The pipeline itself is the cause: it moves the task file
during initialization but then tries to read from the pre-move path when composing
the first agent's prompt.

This blocks the intended end-to-end UX of "open a ticket, run the pipeline on it,
let the agents handle it."

## Reproduction

1. Ensure a task exists at `.af/tasks/open/<TICKET>.md` with `status: open` in frontmatter
2. Run `node dist/cli.js pipeline run sdlc --task <TICKET>`
3. Observe: first phase fails with
   ```
   ✗ Failed to compose prompt: ENOENT: no such file or directory, open '.af/tasks/open/<TICKET>.md'
   ✗ Pipeline sdlc failed at phase "design" for <TICKET>
   ```

Actual repro captured against AF-33 on commit 5c9c69a (2026-04-15):
- Task started at `.af/tasks/open/AF-33.md`
- After failure, task file sat at `.af/tasks/in-progress/AF-33.md`
- `.af/output/AF-33/pipeline-state.json` recorded `failureReason: spawn_error`

## Root cause

In `src/commands/pipeline.ts` (`pipelineRunCommand`):

1. Task is resolved via the provider → `task.filePath` is cached (e.g.
   `.af/tasks/open/AF-33.md`)
2. Step 7 calls `provider.move(task.ticket, 'in-progress')` — this physically renames
   the file on disk and updates its frontmatter
3. Neither `task` nor `task.filePath` is refreshed to reflect the new location
4. Phase loop hands off to the prompt composer, which at
   `src/commands/pipeline.ts:1121` runs:
   ```ts
   const taskContent = readFileSync(args.task.filePath, 'utf-8');
   ```
   …against the now-nonexistent original path → ENOENT

The bug is latent because:
- Unit tests for `provider.move` verify the move itself
- Unit tests for the prompt composer pass a mock `task` with a valid path
- No end-to-end test covers the move-then-compose sequence that the runner actually performs

## Fix (suggested approach — Architect to confirm)

Option A (minimal): After `provider.move`, update `task.filePath` to reflect the new
path. Either compute it inline from the new status directory, or re-fetch via
`provider.get(task.ticket)`.

Option B (cleaner): Resolve the task path lazily inside the prompt composer, from
`task.ticket` via the provider, so the composer never holds a stale path.

Option A is smaller and lower-risk; Option B is more robust if other code paths
develop the same shape.

Either way, add a regression test that exercises the exact sequence:
  resolve task (status: open) → provider.move → read task.filePath

## Acceptance

- [ ] `af pipeline run sdlc --task <TICKET>` on a task with `status: open` reaches the
      first agent spawn without an ENOENT
- [ ] Same for tasks in `ready` or any other valid pre-run status
- [ ] Idempotent on tasks already in `in-progress` (no regression of the
      `if (task.status !== 'in-progress')` skip path)
- [ ] Regression test covers the move-then-read sequence
- [ ] Manual smoke: running the pipeline on AF-33 from a clean state no longer fails
      at phase 1 for this reason

## Notes

- Discovered during the first end-to-end pipeline smoke test (AF-33, 2026-04-15)
- Workaround that unblocks continued testing: pre-move the task to `in-progress/` and
  set `status: in-progress` in frontmatter before invoking `pipeline run`. This skips
  the buggy `provider.move` call.
- Related code: `src/commands/pipeline.ts` lines ~247 (task resolve), ~296-303 (move),
  ~1118-1121 (stale read)
