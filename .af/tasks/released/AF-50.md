# Orchestration output persistence: write OrchestrationResult + per-agent outputs to .af/output/

## Objective
Guarantee that every `af orchestrate` run durably saves its output. Today the
command runs agents in-process, renders a summary table, and **discards every
agent's actual output text** — there is no `result.json`, no per-step file,
nothing on disk. The full content exists in the returned `OrchestrationResult`
but is never written. This ticket makes persistence **structural and always-on**:
you cannot run an orchestration without the result being saved.

## Context
Discovered while reviewing AF-48 test runs (the multi-agent marketing run produced
researcher/analyst/writer output that was lost — only the token table survived).

**Root cause — two execution paths differ:**
- `af agent spawn` runs each agent in a **detached `spawn-runner.js` subprocess**
  that writes `status.json` / `result.md` / `result.json` to `.af/output/<…>`
  (AF-23). Persistence is built into the runner.
- `af orchestrate` runs agents **in-process** via `dispatchAgent` → `runAgent`
  (the deliberate AF-48 decision — the supervisor needs each output synchronously
  to plan the next step). It reused the engine but **skipped the disk-writing half**
  the subprocess runner provides.

The data is already available: `OrchestrationResult` contains every `step.output`,
`step.backend`, `step.usage`, the `finalizers` map, `stopReason`, `approved`, and
`totalUsage` (see `src/lib/orchestrator.ts`).

## Approach (architecture-aligned)
- **Keep the engine pure.** Do NOT add file I/O to `orchestrator.ts` — it stays a
  model-agnostic function returning `OrchestrationResult` (keeps it unit-testable;
  same boundary discipline as AF-48 keeping routing in the CLI).
- **Persist at the command layer** (`src/commands/orchestrate.ts`), reusing the
  existing `.af/output/` convention so it's consistent with `af agent spawn`:
  ```
  .af/output/orchestrate/<domain>/<run-id>/
      result.json                      # full OrchestrationResult (machine-readable)
      step-01-researcher.md            # each delegated agent's output text
      step-02-product-analyst.md
      step-03-content-writer.md
      finalizer-qa.md                  # finalizer outputs
  ```
- **Always-on, not a flag and not dependent on `--json` piping.** Persistence must
  not be optional — that is the "structurally guarded" requirement. (`--json` to
  stdout stays as-is for ad-hoc use.)
- Print the output directory path at the end of the run so the user knows where it
  landed (mirror how spawn surfaces its outputDir).
- `<run-id>`: a stable, sortable id (e.g. timestamp-based). NOTE: derive the id the
  same way other commands timestamp artifacts; follow existing codebase conventions.

## Acceptance
- [ ] Every non-dry-run `af orchestrate` writes `result.json` (the full
      `OrchestrationResult`) under `.af/output/orchestrate/<domain>/<run-id>/`
- [ ] Each delegated step's output text is written to its own `step-NN-<agent>.md`
- [ ] Each finalizer's output is written (`finalizer-<slug>.md` or inside result.json)
- [ ] The run prints the absolute output directory path on completion
- [ ] Persistence is unconditional (no flag required); `--dry-run` writes nothing
      (or writes only the plan, explicitly marked) — decide and document which
- [ ] `orchestrator.ts` remains free of file I/O (engine stays pure); persistence
      lives in `orchestrate.ts` (or a small dedicated writer module it calls)
- [ ] Unit/integration test asserts the files are created with expected content
      from a stubbed `OrchestrationResult` (no live models)
- [ ] Reuse the AF-23 `.af/output/` layout/conventions; do not invent a parallel scheme

## Notes
- Consider whether to gate behind a feature flag during rollout vs ship always-on;
  lean always-on since it's additive and safe.
- Secrets hygiene (AF-48 §7): persist only agent outputs + usage/backend metadata;
  never write endpoints, env, or credentials.
- Pairs with AF-48 (`af orchestrate`) and AF-23 (structured result.json).

## Design
**Technical design:** `docs/designs/AF-50.md` — full spec for the engineer
(file-by-file changes, the `persistOrchestrationResult` writer module + pseudocode,
output layout, error-handling/stdout-fallback, security, test plan).

Summary of the approach:
- **`src/lib/orchestration-output.ts`** (new) — `persistOrchestrationResult(result, {cwd, now?})`
  writes `.af/output/orchestrate/<domain>/<run-id>/` containing `result.json`,
  `summary.md`, `step-NN-<agent>.md` per step, and `finalizer-<slug>.md` per finalizer.
  Returns the run dir. Injectable `now` for deterministic test run-ids.
- **`src/commands/orchestrate.ts`** (edit) — call the writer after `run()` for
  non-dry runs, print `output saved to <dir>`. On write failure: dump full result
  to stdout + exit 1 (output is never lost — the "structurally guarded" requirement).
- **Engine stays pure** — no file I/O in `orchestrator.ts`; persistence at the command
  layer, reusing the AF-23 `.af/output/` convention. **No new feature flag** (intrinsic
  to `af orchestrate`, already gated by `ENABLE_AF_48`; ships always-on).
- **Decision — dry-run persists nothing** (it dispatches nothing; the plan is already
  on stdout and in `result.plan`).
