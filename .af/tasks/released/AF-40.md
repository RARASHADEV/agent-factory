# LokaProvider.get() returned tasks[0] instead of matching ticket — all updates routed to AF-24

## Summary

Every call to `LokaProvider.update()`, `move()`, `assign()`, or `log()` silently
targeted the wrong Loka task. Root cause: `get(ticket)` built a query
`/tasks?projectPrefix=AF&ticketNumber=N` and took `tasks[0]` — but Loka's API
silently ignores the `ticketNumber` param and returns the full project list.
`tasks[0]` was always the first task in Loka's default sort (AF-24 in our
data), so every `update`/`move`/`assign`/`log` PATCHed AF-24.

## Impact

Discovered during the AF-13/AF-18/AF-23/AF-24/AF-28/AF-33/AF-39 housekeeping
sweep. `af sync --mode push` reported "Pushed: 19 task(s)" successfully, but
on Loka only AF-24's status changed — because AF-24 was moved to "Released"
six times in a row instead of the six different intended tickets. AF-24's
title and description were also clobbered by whichever ticket was last
pushed (it ended up with AF-34's title and AF-5's description on Loka).

Secondary impact: any prior status moves done via `af task move` since AF-12
landed probably hit the wrong Loka task too. The bug has existed since the
`get()` method was written.

## Root cause

`src/lib/providers/loka-provider.ts` — `async get(ticket)`:

```ts
// BEFORE (buggy):
const params = { projectPrefix: prefix, ticketNumber: numStr };
const result = await this.client.get('/tasks', params);
// ...
return this.toTask(tasks[0]);   // ← always the same task
```

Loka doesn't implement filtering on `ticketNumber` — it returns the full
project list regardless.

## Fix

Drop `ticketNumber` from the query (the server ignores it anyway) and filter
client-side by `projectPrefix` + `ticketNumber`. Also cross-check
`projectPrefix` to avoid collisions between projects that share a ticket
number.
