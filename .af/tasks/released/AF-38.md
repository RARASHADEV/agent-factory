# Pipeline runner holds stale task handle across phases — agents that move the task file break the next phase

## Summary

`sharedPhaseLoop` receives a `task` object at entry and re-uses the same handle
across every phase in the pipeline. When an agent (e.g. the engineer) moves the
task file during its phase — a normal part of its workflow: `in-progress/` →
`ready-for-qa/` — the next phase's prompt composer reads from the stale
`task.filePath` and fails with ENOENT.

This is the same class of bug as AF-35, just at a different trigger point.
AF-35's fix handled the runner's own initial `provider.move`. It did **not**
handle subsequent moves performed by agents within their phases.

## Reproduction

1. Apply the AF-35 fix (merged in commit `1d4c081`)
2. Apply the AF-36 fix so artifacts persist (merged in commit `04baf9c`)
3. Run `af pipeline run sdlc --task AF-33`
4. Observe:
   - ✅ design phase passes
   - ✅ implement phase passes — engineer moves AF-33 from `in-progress/` → `ready-for-qa/` as part of its work
   - ❌ verify phase fails immediately with:
     ```
     Failed to compose prompt: ENOENT: no such file or directory,
       open '.af/tasks/in-progress/AF-33.md'
     ```

Captured 2026-04-15 on the second smoke-test run of AF-33.

## Root cause

In `src/commands/pipeline.ts`, `sharedPhaseLoop` destructures `task` from its
args once and uses it for every phase iteration. The prompt composer called at
`composeSystemPrompt({ ..., task, ... })` reads `task.filePath` directly. If
agents mutate the filesystem during a phase, the cached `task.filePath` becomes
invalid.

## Fix

Add a re-fetch step at the top of each phase iteration in `sharedPhaseLoop`:

```ts
try {
  const refreshed = await provider.get(task.ticket);
  if (refreshed) {
    task = refreshed;
  }
} catch {
  // Non-fatal: keep prior handle.
}
```

Requires:
- Adding `provider: TaskProvider` to `PhaseLoopArgs`
- Threading `provider` through from `pipelineRunCommand` and `pipelineResumeCommand`
- Changing local `task` from destructured const to reassignable `let`

Placement matters: put the re-fetch **after** the AF-34 pause-sentinel check so
paused runs don't waste a provider call.
