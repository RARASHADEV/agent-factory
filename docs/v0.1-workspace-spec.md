# Agent Factory v0.1 — Workspace Format & CLI

## Goal

Define the workspace file format and build the `af` CLI. No UI, no sync. Just the foundation that agents and humans read/write to.

---

## Workspace Structure

Every project lives in a directory under `~/projects/`. Agent Factory doesn't own the source code — it adds a `.af/` directory to any existing project.

```
~/projects/agent-factory/           # project root (source code lives here)
└── .af/                            # agent factory workspace (dogfooding itself)
    ├── project.md                  # project definition
    ├── tasks/                      # task files organized by status
    │   ├── backlog/
    │   │   └── AF-3.md
    │   ├── open/
    │   ├── in-progress/
    │   │   └── AF-4.md
    │   ├── ready-for-qa/
    │   ├── uat/
    │   ├── ready-4-release/
    │   ├── released/
    │   │   ├── AF-1.md
    │   │   └── AF-2.md
    │   ├── closed/
    │   └── blocked/
    └── context/                    # shared knowledge for this project
        └── v0.1-workspace-spec.md
```

### Global config

```
~/.af/                              # global agent factory config
├── config.yaml                     # global settings
└── templates/                      # project scaffolding templates
```

### Agent Registry (central repo — NOT in project repos)

Agents live in a **dedicated directory** — one central location, separate from any project. Imported once from the agent-platform DB on deva, then maintained as `.md` files locally.

```
~/projects/agent-factory/agents/       # central agent registry
├── code-worker.md
├── product-analyst.md
├── architect.md
├── ora-engineer.md
├── task-planner.md
└── ...
```

Each agent `.md` file contains the full profile as YAML frontmatter:

```markdown
---
slug: code-worker
name: Code Worker
model: sonnet
tools: [read, write, edit, bash, glob, grep]
---

# System Prompt
You are a code worker. You implement features based on task specifications.

# Role Definition
Given a task file with objective, context, and acceptance criteria, produce
working code that satisfies all acceptance criteria.

# Task Instructions
1. Read the full task file and project.md first
2. Explore the existing codebase before writing
3. Follow project conventions (stack, patterns, naming)
4. Log your work in the task's ## Log section

# Output Format
Working code committed to the project. Updated task file with work log.

# Boundaries
- Do not modify files outside the project scope
- Do not change project.md without explicit instruction
- Ask for clarification rather than guessing

# Quality Criteria
- All acceptance criteria checked off
- No regressions in existing functionality
- Code follows existing project patterns

# Escalation Rules
- If acceptance criteria are ambiguous, ask Brahma
- If blocked by a dependency, mark task as blocked
```

**Import from deva (one-time or refresh):**

```bash
af agent sync                          # pulls all agents from deva:5003 → .md files
af agent sync code-worker              # pull a single agent
```

This hits the agent-platform API once, writes/updates the `.md` files, and that's it. Day-to-day, `af` reads local files — zero network calls.

**Source of truth:** The `.md` files are the working copy. The deva DB is the upstream source. Edit locally or in the deva UI — `af agent sync` reconciles.

Tasks reference agents by **slug** (e.g., `assignee: code-worker`). Agent Factory resolves the slug to `~/projects/agent-factory/agents/code-worker.md`. No agent files in project repos. No API calls at spawn time.

## File Formats

### project.md

```markdown

id: agent-factory

origin: ORA-150             # optional: where the idea came from

CLI + workspace engine for managing AI agent workflows across projects.

## Goals
- File-based workspace format (.af/) that any project can adopt
- CLI for task and agent management
- Agent spawn: compose prompt from agent profile + task + context → Claude subprocess

## Decisions
```

### Task file (e.g. AF-4.md)

```markdown
---
ticket: AF-4
title: Task CRUD CLI commands
type: feature              # bug | chore | epic | feature | improvement | task
status: in-progress        # backlog | open | in-progress | ready-for-qa | uat | ready-4-release | released | closed | blocked
priority: high             # critical | high | medium | low
complexity: medium         # low | medium | high
assignee: code-worker      # agent slug or "brahma"
depends: [AF-3]            # optional: informational — why it's blocked
due: 2026-03-14            # optional: YYYY-MM-DD
created: 2026-03-07
updated: 2026-03-07
---

# Task CRUD CLI commands

## Objective
Implement `af task list|create|show|move|assign` commands.

## Context
- Tasks are markdown files with YAML frontmatter in `.af/tasks/{status}/`
- Moving a task = moving the file between status directories + updating frontmatter
- Valid statuses: backlog, open, in-progress, ready-for-qa, uat, ready-4-release, released, closed, blocked
- Ticket numbers auto-increment from project.md counter field

## Acceptance
- [ ] `af task list` shows all tasks with status, priority, assignee
- [ ] `af task create "title"` scaffolds a new .md in backlog/
- [ ] `af task show AF-4` prints the full task file
- [ ] `af task move AF-4 done` moves file + updates frontmatter
- [ ] `af task assign AF-4 code-worker` sets assignee in frontmatter

Agents check boxes as they complete each criterion. `af task move <ticket> done` verifies all boxes are checked before allowing the move.

## Log
- [2026-03-07T14:20:00Z] code-worker: started | Reading workspace spec.
- [2026-03-07T14:35:00Z] code-worker: completed | Implemented list and create commands.
- [2026-03-07T14:50:00Z] code-worker: completed | All 5 subcommands working. Tests pass.
```

## CLI Commands (v0.1 scope)

All commands operate on the current directory's `.af/` workspace, or accept `--project <prefix>`.

### Project management

```bash
af init <prefix> [--name "Project Name"]
# Creates .af/ directory with project.md scaffold
# Adds project to ~/.af/config.yaml

af projects
# Lists all registered projects with status and task counts

af status [--project AF]
# Shows task breakdown by status (backlog, open, in-progress, etc.)
# Shows in-progress tasks with assignees
```

### Task management

```bash
af task list [--status in-progress] [--assignee code-worker]
# Lists tasks, filterable by status/assignee/priority

af task create <title> [--type feature] [--priority high] [--complexity medium] [--assignee code-worker] [--depends AF-3] [--due 2026-03-14]
# Creates a new task .md file in backlog/
# Auto-increments ticket number from project.md counter
# Defaults: type=task, priority=medium, complexity=medium

af task show AF-4
# Prints the full task file

af task move AF-4 in-progress
# Moves task file between status directories
# Updates frontmatter status + updated timestamp

af task assign AF-4 code-worker
# Sets assignee in frontmatter
```

### Agent management

```bash
af agent list
# Lists agents from local registry (~/projects/agent-factory/agents/)
# Shows slug, name, model

af agent show code-worker
# Prints the full agent .md file
# Displays all instruction fields

af agent sync [slug]
# Pulls agent profiles from agent-platform API (deva:5003) → local .md files
# Without slug: syncs all. With slug: syncs one.

af agent spawn code-worker --task AF-4
# Reads agent .md from local registry (no API call)
# Composes prompt from instruction fields + task file + project.md + context/
# Spawns claude CLI subprocess via SDK
# Streams output to terminal
# On completion: updates task log and moves to done/
```

## Spawn mechanics

When `af agent spawn` runs:

1. **Resolve agent** — read agent `.md` from local registry (`~/projects/agent-factory/agents/code-worker.md`)
2. **Load context** — read task `.md` + `project.md` + relevant `context/` files
3. **Compose prompt** — build system prompt from agent's instruction fields → inject project context → task details
4. **Spawn** — `claude --system-prompt <composed> --message "Execute the task described above"` (or equivalent SDK call)
5. **Stream** — pipe stdout/stderr to terminal
6. **On exit** — parse agent's task updates, move file if done, log result

Context budget: agent template (~200 tokens) + task (~300 tokens) + project.md (~200 tokens) + context files (variable). Target: <2K tokens base, scaling with context/ size.

The agent subprocess has full filesystem access to the project root via Claude Code's tools. It reads/writes source code directly. The `.af/` workspace is just the briefing — the agent works on the real codebase.

## Task frontmatter contract

| Field | Required | Type | Values |
|-------|----------|------|--------|
| `ticket` | yes | string | `{PREFIX}-{N}` |
| `title` | yes | string | — |
| `type` | yes | enum | `bug`, `chore`, `epic`, `feature`, `improvement`, `task` |
| `status` | yes | enum | `backlog`, `open`, `in-progress`, `ready-for-qa`, `uat`, `ready-4-release`, `released`, `closed`, `blocked` |
| `priority` | yes | enum | `critical`, `high`, `medium`, `low` |
| `complexity` | yes | enum | `low`, `medium`, `high` |
| `assignee` | no | string | agent slug or `"brahma"` |
| `depends` | no | list | ticket IDs — informational context for blocks |
| `due` | no | date | `YYYY-MM-DD` |
| `created` | yes | date | `YYYY-MM-DD` |
| `updated` | yes | date | `YYYY-MM-DD` |

### Blocking rules

- **`status: blocked` = do not spawn.** Full stop. `af agent spawn` refuses to run on blocked tasks.
- `depends` is informational — it documents *why* something is blocked, but the gate is the status field.
- Unblocking is always a deliberate act: `af task move <ticket> open`.

### Acceptance criteria

- Agents check boxes (`- [x]`) as they satisfy each criterion during execution.
- `af task move <ticket> done` verifies all boxes are checked. Fails if any remain unchecked.

### Log format

Structured entries: `[ISO-timestamp] agent-slug: action | message`

Actions: `started`, `completed`, `blocked`, `note`

## File conventions

| Rule | Rationale |
|------|-----------|
| YAML frontmatter is the structured index | Agents and CLI parse it; humans read the body |
| Ticket numbers are `{PREFIX}-{N}` | Same convention as Loka |
| Status directories are canonical | File location = status. Frontmatter mirrors it. 9 dirs: backlog, open, in-progress, ready-for-qa, uat, ready-4-release, released, closed, blocked |
| Log section is append-only | Agents add entries, never modify or delete existing ones |
| context/ files are shared knowledge | Any agent working on the project can reference them |
| Agent profiles are centralized | Stored as `.md` files in agent-factory repo, not in project repos |
| Agent spawns are stateless | No memory between runs. Context comes from task + project files |

## What v0.1 does NOT include

- No web UI (that's v0.3)
- No Loka sync (that's v0.4)
- No multi-agent orchestration or DAGs
- No conversation persistence (agent sessions are fire-and-forget)
- No auth or multi-user — this is Brahma's machine
