# AF-10: Cross-project CLI view — `af status --all`

## Overview

Add an `--all` flag to the existing `af status` command that aggregates task status across all registered projects. The command uses the existing project registry (`~/.af/config.yaml`) for project discovery — no new registry file needed. Output is a colored summary table showing each project's task counts by status category, plus a list of blocked items. Works from any directory since it reads the global config.

## Architecture

### Components Affected

1. **`src/commands/status.ts`** — Add `--all` flag handling; new `statusAllCommand()` function
2. **`src/cli.ts`** — Add `--all` / `-a` option to status command definition
3. **`src/lib/format.ts`** — Add table formatting helper for cross-project view

### Flow

```
af status --all
  → loadConfig()                    # read ~/.af/config.yaml
  → config.projects[]               # iterate registered projects
  → for each project:
      → loadProject(afPath)         # get project metadata
      → listTasks(afPath)           # get all tasks
      → aggregate counts by status category
  → render summary table
  → render blocked items section
```

### Project Discovery Decision

**Use existing `~/.af/config.yaml` registry** (the `projects[]` array). Rationale:
- Already populated by `af init` — every project is auto-registered
- `listProjects()` already resolves paths + loads metadata
- No need for a separate `~/.af/projects.json` or filesystem scanning
- The `af projects` command already uses this same source

Auto-discovery (`~/projects/*/.af/`) is NOT needed — it would be slower, less reliable, and the registry already covers all initialized projects. If a project isn't in the registry, the user should run `af init`.

## API Design

### CLI Interface

```
af status --all    # cross-project aggregated view
af status -a       # short form
af status          # existing: current project only (unchanged)
af status -p AF    # existing: specific project (unchanged)
```

**Option conflict:** `--all` and `--project` are mutually exclusive. If both provided, print error and exit.

### Output Format

#### Summary Table

Use `cli-table3` (already in `package.json` but unused) for clean alignment:

```
Cross-project Status

  Project          Open  In-Progress  Blocked  Done  Total
  ─────────────────────────────────────────────────────────
  AF  agent-factory   2           3        0     5     13
  LOK loka            4           1        1     2      9
  OB  oracle-bridge   0           0        0     3      3
  AST astra           1           2        0     0      5
  ─────────────────────────────────────────────────────────
  Totals              7           6        1    10     30
```

Columns:
- **Project**: prefix + name (prefix bold, name dim)
- **Open**: count of `open` + `backlog` status tasks
- **In-Progress**: count of `in-progress` tasks
- **Blocked**: count of `blocked` tasks (red if > 0)
- **Done**: count of `released` + `closed` tasks
- **Total**: all tasks

#### Blocked Items Section

If any blocked tasks exist across projects, append:

```
  Blocked Items
    🐛 LOK-15  Fix auth timeout  [blocked]  high  @engineer   (LOK)
```

Each line uses existing `formatTaskLine()` with project prefix appended.

#### Empty State

If no projects registered:
```
No projects registered. Run `af init <prefix>` in a project directory.
```

If projects exist but no tasks:
```
Cross-project Status

  No tasks found across 3 registered projects.
```

## Data Model

No new data models or storage. This feature is read-only, consuming:
- `~/.af/config.yaml` → `projects[]` (existing)
- `.af/project.md` per project → `ProjectMeta` (existing)
- `.af/tasks/<status>/*.md` per project → `TaskMeta` (existing)

### Intermediate Aggregation Structure (in-memory only)

```typescript
interface ProjectSummary {
  prefix: string;
  name: string;
  path: string;
  counts: {
    open: number;       // open + backlog
    inProgress: number; // in-progress
    blocked: number;    // blocked
    done: number;       // released + closed
    total: number;
  };
  blockedTasks: TaskMeta[];  // for the blocked section
}
```

## Implementation Notes

### 1. Modify `src/commands/status.ts`

- Add `all` to `StatusOptions` interface: `all?: boolean`
- At top of `statusCommand()`, check `options.all`:
  - If true, call new `statusAllProjects()` function and return
  - If `options.all && options.project`, print error and exit
  - Otherwise, fall through to existing single-project logic
- New function `statusAllProjects()`:
  - Call `listProjects()` from workspace lib
  - For each project, call `listTasks(project.afPath)`
  - Compute `ProjectSummary` for each
  - Render table using `cli-table3`
  - Render blocked items if any

### 2. Modify `src/cli.ts`

Add the `--all` option to the status command:

```typescript
program
  .command('status')
  .description('Show task breakdown for a project')
  .option('-p, --project <prefix>', 'Project prefix (defaults to cwd)')
  .option('-a, --all', 'Show status across all registered projects')
  .action(statusCommand);
```

### 3. Table Rendering (`src/lib/format.ts`)

Add a helper or use `cli-table3` directly in the status command. Prefer using `cli-table3` since it's already a dependency:

```typescript
import Table from 'cli-table3';

const table = new Table({
  head: ['Project', 'Open', 'In-Progress', 'Blocked', 'Done', 'Total'],
  style: { head: ['dim'] },
  chars: { /* minimal border chars */ }
});
```

### 4. Status Bucketing

Group the 9 statuses into 4 display columns:
- **Open**: `backlog` + `open`
- **In-Progress**: `in-progress` + `ready-for-qa` + `uat` + `ready-4-release`
- **Blocked**: `blocked`
- **Done**: `released` + `closed`

This matches the acceptance criteria ("open/in-progress/done counts, blocked items").

### 5. Error Handling

- **Missing project path**: If a registered project's path no longer exists, skip it and print a dim warning: `⚠ Project FOO path not found, skipping`
- **Unreadable .af/**: Skip with warning
- **No projects**: Friendly empty-state message
- **--all + --project conflict**: Print error, exit 1

### 6. Performance

All I/O is synchronous (matching existing patterns). For typical usage (< 10 projects, < 100 tasks each), this is fine. No need for async/parallel optimization.

### 7. Works From Any Directory

The `--all` flag bypasses `resolveProject()` entirely — it calls `listProjects()` which reads the global config with absolute paths. No cwd dependency.

## COO Constraints (Ora)

These constraints override or narrow the design above. Engineers must follow them.

1. **Implement as `--detail` flag on existing `af projects` command, NOT as `af status --all`.** The `af projects` command already exists and shows per-project task counts via `listProjects()`. This feature is an enhancement to that — adding task-level detail grouped by status. Adding a whole new command path when the plumbing already lives in `af projects` is unnecessary.

2. **Concrete change:** Add `--detail` / `-d` flag to `af projects`. Without the flag, behavior is unchanged (existing summary). With the flag, show the full table (prefix, name, open/in-progress/blocked/done/total) plus the blocked items section as designed above.

3. **No new command.** Do not create a `status --all` path. Do not modify `src/commands/status.ts`. Work entirely within `src/commands/projects.ts` (or wherever `af projects` lives).

4. **Everything else in the design stands** — the table format, `cli-table3` usage, status bucketing, blocked items section, error handling, empty states. Just wire it into `af projects --detail` instead of `af status --all`.
