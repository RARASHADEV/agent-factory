# AF-51: Sanitize Inherited CLAUDE_CODE_* Env on SDK Spawn — Technical Design

> Make AF's Claude backend work when AF is launched **from inside an existing
> Claude Code session**. Today the inherited `CLAUDE_CODE_*` env vars leak into the
> nested `query()` subprocess and crash it. Fix: pass a **sanitized environment** to
> the spawned process. **Small, centralized, low-risk.**

**Author:** Architect · **Date:** 2026-06-02 · **Implementation role:** ENGINEER (backend/CLI only) · **Complexity:** low · **Depends on:** AF-48 (shipped)

---

## 1. Overview

When AF runs a Claude-backed agent it spawns a nested Claude Code process via
`@anthropic-ai/claude-agent-sdk` `query()` (`src/lib/sdk.ts` → `runAgent`). If the
**parent** shell is itself a Claude Code session, it has set runtime-identity env
vars (session id, entrypoint, exec path, temp dir, effort, agent markers). The child
inherits them, gets confused about whether it is a new session or the parent, and
exits: `Claude Code process exited with code 1`.

**Verified during AF-48 live testing:** clearing those vars made the SDK succeed
immediately (a 4-agent orchestration ran cleanly). So this is purely environmental —
no logic bug. The repeated workaround was:

```bash
env -u CLAUDECODE -u CLAUDE_CODE_ENTRYPOINT -u CLAUDE_CODE_SESSION_ID \
    -u CLAUDE_CODE_AGENT -u CLAUDE_CODE_EXECPATH -u CLAUDE_CODE_TMPDIR \
    -u AI_AGENT -u CLAUDE_EFFORT  node dist/cli.js orchestrate …
```

AF-51 makes that automatic so the workaround is never needed.

### Key facts that shape the fix
- The SDK `query()` options accept **`env?: { [k]: string | undefined }`**, which
  *"Defaults to `process.env`"* (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:746-759`).
  Passing `env` **replaces** the default — so we must pass a **full copy of
  `process.env` minus the deny-listed keys**, not just a few keys (else the child
  loses `PATH`/`HOME`/auth).
- The detached-subprocess path already *attempts* this but incompletely:
  `src/commands/agent.ts:307` spawns with `env: { ...process.env, CLAUDECODE: undefined }`
  — it nulls **only** `CLAUDECODE`, leaving the other 7 vars to leak. (And that
  subprocess later calls `runAgent` → `query()` with default env anyway.)
- Auth is **file-based** (`~/.claude`), not env-based, so stripping these vars does
  **not** affect login.

## 3. Architecture

Both Claude-backed execution paths converge on `runAgent` → `query()`:

```
af orchestrate ─→ dispatchAgent ─┐
af agent spawn ─→ spawn-runner ─→ dispatchAgent ─┤─→ runAgent (sdk.ts) ─→ query({ env: SANITIZED })
                                                  └──────────────── single choke point ───────────────┘
```

So the **authoritative fix is one line at the `query()` call** — it covers both
paths. The `agent.ts` detached-spawn env is upgraded to the same helper as secondary
hygiene (so the subprocess starts clean even before it reaches `runAgent`).

### What we do NOT touch
- We do **not** mutate the parent `process.env` (no global side effects; the calling
  session is untouched).
- We do **not** change agent prompts/context — agents still receive their full task
  context via the prompt, exactly as before. (This directly answers "do we lose
  context?": no — these vars never carried context.)

## 4. New Module: `src/lib/env-sanitize.ts`

```ts
/**
 * AF-51: Env vars a parent Claude Code session sets that must NOT leak into a
 * nested SDK-spawned Claude process (they make the child think it is the parent
 * session and exit with code 1). Identity/runtime markers only — NOT auth
 * (auth is file-based in ~/.claude) and NOT PATH/HOME/locale.
 */
export const CLAUDE_SESSION_ENV_DENYLIST = [
  'CLAUDECODE',
  'CLAUDE_CODE_ENTRYPOINT',
  'CLAUDE_CODE_SESSION_ID',
  'CLAUDE_CODE_AGENT',
  'CLAUDE_CODE_EXECPATH',
  'CLAUDE_CODE_TMPDIR',
  'AI_AGENT',
  'CLAUDE_EFFORT',
] as const;

/**
 * Build an environment for a nested Claude process: a full copy of `base`
 * (default process.env) with the deny-listed session markers removed. Everything
 * else — PATH, HOME, auth, locale, user vars — is preserved.
 */
export function sanitizedSpawnEnv(
  base: NodeJS.ProcessEnv = process.env,
): NodeJS.ProcessEnv {
  const out: NodeJS.ProcessEnv = { ...base };
  for (const key of CLAUDE_SESSION_ENV_DENYLIST) delete out[key];
  return out;
}
```

Pure function, trivially testable, single source of truth for the deny-list.

## 5. Call-site Changes

### 5.1 `src/lib/sdk.ts` (authoritative)
Add `env` to the `query()` options:

```ts
import { sanitizedSpawnEnv } from './env-sanitize.js';
// ...
const stream = query({
  prompt: taskPrompt,
  options: {
    systemPrompt,
    model: options.model || 'sonnet',
    // ...existing options unchanged...
    persistSession: false,
    env: sanitizedSpawnEnv(),   // AF-51: strip inherited Claude-session markers
  },
});
```

### 5.2 `src/commands/agent.ts` (consistency)
Replace the partial ad-hoc strip at line ~307:

```ts
// before:
env: { ...process.env, CLAUDECODE: undefined },
// after:
env: sanitizedSpawnEnv(),   // AF-51: full deny-list, not just CLAUDECODE
```

No other call sites spawn Claude. (`spawn-runner.js` reaches Claude only via
`runAgent`, so 5.1 already covers it.)

## 6. Error Handling

No new failure modes. If a deny-listed var is absent (the normal case — running from
a plain terminal), `delete` is a harmless no-op and behavior is identical to today.
The fix is purely subtractive on the child env.

---

## 7. Security Considerations

- **Strictly reduces** what the child inherits — never adds. No new surface.
- The deny-list is an **explicit allow-everything-except list**, so `PATH`, `HOME`,
  locale, and the file-based `~/.claude` auth are preserved (auth keeps working).
- Do **not** broaden to a wildcard `CLAUDE_CODE_*` prefix strip without checking the
  SDK's documented config vars — a blanket strip could remove a var the child
  legitimately needs. The 8 explicit keys are the empirically verified set.

## 8. Test Plan

**Unit — `src/__tests__/env-sanitize.test.ts` (new):**
- Given a base env containing all 8 deny-listed keys **plus** `PATH`, `HOME`, and a
  custom `FOO`: result omits all 8 and retains `PATH`/`HOME`/`FOO`.
- Given a base env with none of them: result deep-equals the input (no-op).
- Does not mutate the input object (returns a copy; `base` unchanged).
- `CLAUDE_SESSION_ENV_DENYLIST` includes each of the 8 known keys.

**Integration / manual (documented in ticket log):**
- From **inside** a Claude Code session (the `CLAUDE_CODE_*` vars present), run
  `af orchestrate marketing "<objective>" --max-delegations 1` (flag on) **without**
  any `env -u` prefix → the run dispatches successfully (no `exited with code 1`),
  per-step `backend: claude`. This is the real acceptance signal.
- `af agent spawn` smoke from inside a session → completes, writes `result.md`.

**Regression:** full suite green; `tsc --noEmit` clean; behavior unchanged when the
vars are absent (normal terminal).
