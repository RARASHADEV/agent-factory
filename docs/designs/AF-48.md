# AF-48: Wire Orchestrator to a Production Entry Point — Technical Design

> Connects the already-built orchestration engine (AF-46) to real execution (AF-42) and exposes it to users via `af orchestrate`. No new engine logic — this is **glue + a CLI command + a feature flag**.

**Author:** Architect · **Date:** 2026-05-31 · **Implementation role:** ENGINEER (backend/CLI only) · **Complexity:** medium

---

## 1. Overview

Today the orchestration engine ships as a library with an **unwired seam**. Three pieces exist and are unit-tested in isolation, but nothing connects them and there is no way for a user to run them:

| Piece | File | Status |
|-------|------|--------|
| Backend router | `src/lib/execution.ts` → `dispatchAgent(config, opts)` returns `{ backend, output, usage, success }` | ✅ exists (AF-42) |
| Executor seam | `src/lib/executor.ts` → `AfCliExecutor` takes an injected `AfCliDispatch`, threads `backend` | ✅ exists (AF-45) |
| Orchestrator | `src/lib/orchestrator.ts` → `createOrchestrator(executor)`, `Orchestrator.run(domain, objective, opts)` | ✅ exists (AF-46) |

**The missing link:** nobody builds a concrete `AfCliDispatch` that resolves an agent slug → its `execution` frontmatter → `dispatchAgent`. So `AfCliExecutor` is never constructed in production, the AF-FIX-A6 per-step `backend` attribution is never exercised, and there is no `af orchestrate` command.

This design adds exactly three things:

1. **`src/lib/af-dispatch.ts`** — a `createAfCliDispatch()` factory producing the concrete `AfCliDispatch` (the glue).
2. **`src/commands/orchestrate.ts`** — the `af orchestrate <domain> <objective>` command that builds `AfCliExecutor` → `Orchestrator` → runs it → prints a report.
3. **`ENABLE_AF_48`** feature flag (default **off**) + CLI registration in `src/cli.ts`.

### Key architectural decision: in-process, not subprocess

`af agent spawn` detaches a background subprocess (`spawn-runner.js`) and returns immediately. **Orchestration does NOT use that path.** The orchestrator must receive each agent's `output` + `usage` synchronously to make the supervisor's next decision. Therefore the dispatch surface calls `dispatchAgent` **in-process** (Claude path uses the SDK `runAgent` in-process; local path uses `fetch` in-process — both already in-process inside `dispatchAgent`). This is the correct and simplest fit; do not reuse the subprocess machinery.

## 3. Architecture

### Call graph

```
af orchestrate marketing "Launch the spring campaign"
  │
  ▼
src/commands/orchestrate.ts::orchestrateCommand(domain, objective, opts)
  │
  ├── guard: ENABLE_AF_48 (else friendly "not enabled" message, exit 0)
  ├── resolveProject() / config.defaults.model           ← existing
  │
  ├── dispatch = createAfCliDispatch({                    ← AF-48 NEW (src/lib/af-dispatch.ts)
  │       cliDefaultModel: config.defaults.model,
  │       cwd: process.cwd(),
  │   })
  ├── executor = new AfCliExecutor({ dispatch })          ← AF-45 (existing)
  ├── orchestrator = createOrchestrator(executor)         ← AF-46 (existing)
  │
  ├── result = await orchestrator.run(domain, objective, {
  │       dryRun, maxDelegations, domainsDir,
  │       logger: line => console.log(dim(line)),         ← stream plan/trace live
  │   })
  │     │
  │     ▼  (inside orchestrator, per delegated agent)
  │     executor.run(slug, input)
  │       └── dispatch(slug, input):                       ← the AF-48 glue
  │             ├── loadAgent(slug)            → throws if missing  ← agent.ts (existing)
  │             ├── resolveExecution(meta.execution)                ← execution.ts (existing)
  │             ├── applyCliDefaultModel(execCfg, cliDefaultModel)  ← execution.ts (existing)
  │             ├── compose systemPrompt (agent body) + taskPrompt (objective+context)
  │             └── dispatchAgent(execCfg, {...})  → { backend, output, usage, success }
  │
  └── render report: stopReason, approved, per-step backend table, totalUsage, finalizers
        (or raw JSON when --json)
```

### Why a factory with injected dependencies

`createAfCliDispatch()` takes its two collaborators (`loadAgent`, `dispatchAgent`) as **optional injected params defaulting to the real implementations**. This keeps the glue unit-testable with no disk reads and no network — matching how `AfCliExecutor`/`StubExecutor` and `dispatchLocal`'s `fetchImpl` already do DI in this codebase.

## 4. New Module: `src/lib/af-dispatch.ts`

```ts
import { loadAgent as realLoadAgent } from '../commands/agent.js';
import {
  resolveExecution, applyCliDefaultModel, dispatchAgent,
} from './execution.js';
import type { AgentInput } from './executor.js';

export interface AfCliDispatchOptions {
  /** CLI default model (e.g. config.defaults.model). Applied per applyCliDefaultModel rules. */
  cliDefaultModel?: string;
  /** Working directory passed to the Claude backend path. */
  cwd?: string;
  /** DI seams for tests — default to the real implementations. */
  loadAgentFn?: typeof realLoadAgent;
  dispatchFn?: typeof dispatchAgent;
}

/** Build the concrete AfCliDispatch the production AfCliExecutor binds to. */
export function createAfCliDispatch(opts: AfCliDispatchOptions = {}) {
  const loadAgentFn = opts.loadAgentFn ?? realLoadAgent;
  const dispatchFn  = opts.dispatchFn  ?? dispatchAgent;

  return async (agentId: string, input: AgentInput) => {
    const agent = loadAgentFn(agentId);
    if (!agent) {
      throw new Error(
        `orchestrate: agent "${agentId}" not found in registry ` +
        `(expected agents/${agentId}.md). Run \`af agent sync\` or check the domain roster.`,
      );
    }

    // Routing lives in AF CLI (execution.ts). We only resolve + hand off.
    const execCfg = resolveExecution(agent.meta.execution);
    execCfg.model = applyCliDefaultModel(execCfg, opts.cliDefaultModel);

    const systemPrompt = agent.content.trim();
    const taskPrompt = composeTaskPrompt(input);

    const result = await dispatchFn(execCfg, {
      systemPrompt,
      taskPrompt,
      maxTurns: agent.meta.maxTurns,
      tools: agent.meta.tools,
      cwd: input.cwd ?? opts.cwd,
      // timeoutMs intentionally omitted → dispatchAgent/process guard defaults apply.
    });

    // Pass backend through so the orchestrator records it per step (AF-FIX-A6).
    return { output: result.output, usage: result.usage, backend: result.backend };
  };
}

/** Render an AgentInput into a single task prompt. */
function composeTaskPrompt(input: AgentInput): string {
  const parts = [input.objective.trim()];
  if (input.context !== undefined && input.context !== null) {
    parts.push('', '## Context', '```json', JSON.stringify(input.context, null, 2), '```');
  }
  return parts.join('\n');
}
```

**Notes for the engineer:**
- `loadAgent` is already exported from `src/commands/agent.ts` (line 41) and returns `{ meta, content, filePath } | null`. Reuse it; do not re-implement frontmatter parsing.
- `AgentInput` is `{ objective: string; context?: unknown; cwd?: string }` (`executor.ts`).
- The returned object's shape **must** match the `AfCliDispatch` contract in `executor.ts` (`{ output, usage, backend? }`). `AfCliExecutor.run` normalizes `usage` and copies `backend` onto `AgentResult` — no change needed there.
- Do **not** add model/backend branching here. `dispatchAgent` owns routing (design §2.1). This module only resolves frontmatter and hands off.

## 5. New Command: `src/commands/orchestrate.ts`

### Signature & options

```ts
export interface OrchestrateOptions {
  dryRun?: boolean;
  maxDelegations?: string;   // commander passes strings → parseInt
  domainsDir?: string;       // override for tests / non-default layout
  project?: string;
  json?: boolean;
}

export async function orchestrateCommand(
  domain: string,
  objective: string,
  options: OrchestrateOptions,
): Promise<void>
```

### Behavior

1. **Feature flag:** if `!ENABLE_AF_48`, print `Orchestration is not enabled (ENABLE_AF_48=false).` and `return` (exit 0 — not an error).
2. Resolve project/defaults to obtain `config.defaults.model` (reuse existing `resolveProject` helper used by `agent spawn`/`pipeline`).
3. Build `dispatch` → `executor` → `orchestrator` per the call graph (§3).
4. `await orchestrator.run(domain, objective, { dryRun, maxDelegations, domainsDir, logger })`.
   - `logger` streams each plan/trace line via `console.log(dim(line))` so the user sees progress live.
   - `maxDelegations` parsed with `parseInt(options.maxDelegations, 10)` only when provided.
5. **Render:**
   - `--json` → `console.log(JSON.stringify(result, null, 2))` and return.
   - Otherwise a human report:
     - header: `domain`, `objective`, `DRY RUN` marker if applicable
     - per-step table: `#  agent  backend  tokens(in/out)`
     - finalizers: each slug + `approved`/verdict
     - footer: `stopReason`, `approved`, `steps`, `totalUsage`
6. **Exit code:** `0` when the run completes (even if `approved=false` or a guardrail stopped it — those are *outcomes*, surfaced in the report, not crashes). Reserve non-zero for thrown errors (§6).

### CLI registration (`src/cli.ts`)

```ts
import { orchestrateCommand } from './commands/orchestrate.js';

program
  .command('orchestrate <domain> <objective>')
  .description('Run a domain orchestration (supervisor + roster) end-to-end')
  .option('--dry-run', 'Log the plan without dispatching any agent')
  .option('--max-delegations <n>', 'Override the domain policy max_delegations')
  .option('--domains-dir <path>', 'Override the orchestration/domains directory')
  .option('--json', 'Emit the raw OrchestrationResult as JSON')
  .option('-p, --project <prefix>', 'Project prefix')
  .action(orchestrateCommand);
```

## 6. Error Handling

| Condition | Source | Handling |
|-----------|--------|----------|
| `ENABLE_AF_48=false` | flag guard | Friendly message, **exit 0** |
| Empty/invalid `objective` or `domain` | `OrchestrationInputError` (orchestrator §6.1) | Print `err.errors` joined, **exit 1** |
| Domain file missing / invalid / roster slug unresolved | `DomainConfigError` (validator) | Print `err.message` + validation list, **exit 1** |
| Agent in roster has no `agents/<slug>.md` | `createAfCliDispatch` throw | Clear message naming the slug, **exit 1** |
| Domain uses `backend: local` but `ENABLE_AF_42=false` | `dispatchAgent` throw | Surface message, **exit 1** |
| Local endpoint not in allow-list | `validateEndpoint` (SSRF guard) | Surface message, **exit 1** |
| Guardrail stop (`max_delegations`, `token_budget`, `timeout`, `no_progress`, `max_revisions`) | normal result | **Not an error** — shown as `stopReason` in report, exit 0 |
| `approved=false` from a finalizer | normal result | Shown in report, exit 0 |

Wrap the `orchestrator.run` call in `try/catch`; on catch, print `chalk.red(err.message)` and `process.exitCode = 1`. Do not leak stack traces to stdout (match existing command conventions).

## 7. Security Considerations

- **SSRF:** No new network surface. The only outbound calls happen inside `dispatchAgent` → `dispatchLocal`, which already enforces `validateEndpoint` against `LOCAL_ENDPOINT_ALLOWLIST` (AF-42, §8). The glue passes the agent's own `execution.endpoint` through unchanged; it cannot widen the allow-list.
- **Roster confinement:** the orchestrator's `roster_only` guardrail (default on) already rejects any supervisor attempt to delegate outside the declared roster. The dispatch layer additionally fails closed if a slug has no agent file. There is no path for arbitrary agent execution.
- **Prompt composition:** `objective` is user input embedded into the task prompt — identical trust model to `af agent spawn --prompt`. No new injection class introduced. Objective is validated non-empty before any dispatch.
- **No secrets in output:** the `--json` and report renderers emit only `agent`, `backend`, token counts, and outputs the agent itself produced; do not log endpoints, env, or model credentials.

## 8. Implementation Notes

1. **Supervisor must emit parseable decisions (dependency, not code in this ticket).** The default planner (`executorPlanner`) feeds the supervisor agent its context (roster/history/goal) and parses output via `parseSupervisorDecision`, which accepts `{done:true}`, `{calls:[{agent,input?}]}`, or a single-call shorthand `{agent}` — as an object **or a JSON string**. For a real run to delegate, the supervisor **agent markdown** must instruct the model to emit that JSON. This is content authoring, not AF-48 code — but the engineer should verify at least one supervisor agent + domain emits parseable decisions when doing manual verification, and flag to the Product Analyst if no such supervisor agent exists yet.
2. **`--dry-run` already does the right thing in the engine.** `executorPlanner` in dryRun emits a static plan and returns `done` with zero usage; `executeCalls`/`runFinalizers` log `[dry-run] would …` lines and dispatch nothing. The command just needs to pass `dryRun: true` and render the `plan` array. No live backend is touched.
3. **Reuse, don't duplicate:** `loadAgent`, `resolveExecution`, `applyCliDefaultModel`, `dispatchAgent`, `createOrchestrator`, `AfCliExecutor` are all existing exports. AF-48 writes **no** new execution/normalization/guardrail logic.
4. **`maxDelegations` parsing:** commander gives strings. Only pass `maxDelegations` to `run()` when the option is present and parses to a finite number; otherwise omit so the domain policy value applies.
5. **Project resolution:** mirror how `pipeline.ts`/`agent.ts` obtain `config.defaults.model` and `cwd`; do not invent a new project-resolution path.

## 10. Feature Flag Specification

| Field | Value |
|-------|-------|
| **Flag** | `ENABLE_AF_48` |
| **Location** | `src/lib/constants.ts` (alongside `ENABLE_AF_42`) |
| **Default** | `false` (off until verified against a real local model + a supervisor that emits parseable decisions) |
| **Guards** | The entire `af orchestrate` command. When off: friendly message, exit 0. Engine/library code is **not** gated (it's already merged and tested); only the user-facing command is gated. |
| **Flip-on criteria** | Manual run against a local Ollama/vLLM domain produces a populated per-step `backend`, a sane `stopReason`, and measured `totalUsage`. Documented in the AF-48 ticket log. |

Note: `af orchestrate` against a `local` domain also requires `ENABLE_AF_42=true` (already true). A `claude`-backed domain needs only `ENABLE_AF_48`.
